- PB-IS-015.5-R2 Financial Transactions Ordering and Selection Consistency Repair implemented after empirically confirming (real Dexie, not hypothesis) that `/income` and `financial_transactions` diverged on same-date ties. Root cause: `/income` orders exclusively through `incomeService.listServiceIncomes({ newestFirst: true })` → `db.services.orderBy('date').reverse()`, whose reverse IndexedDB cursor resolves equal-date ties in descending primary-key (id) order; `financial_transactions` instead fetched ascending (`newestFirst: false`) and re-sorted with its own stable `Array.prototype.sort` comparator (`sortTransactions`), which preserves ascending order on ties — the exact opposite of `/income` whenever two or more incomes share a date (common, since `date` has day-level granularity only). Reproduced with three same-date incomes (A, B, C, created in that order): `/income` shows `C, B, A`; the tool previously returned `A, B, C`. Fix in `transactionsTool.ts`: (1) the income/expense fetch now derives `newestFirst` from the requested sort direction instead of a hardcoded `false`, aligning the base query with the same certified call `/income`/`/expenses` use; (2) `sortTransactions` gained a `recordId` tie-break (the record's real numeric id) applied with the same direction factor as the primary field, reproducing Dexie's actual reverse/forward cursor tie-break semantics instead of relying on `Array.sort` stability as an implicit (and wrong) tie-break. No second ordering engine or duplicated "latest incomes" definition was introduced; the tool still sources exclusively from `incomeService`/`expenseService`, now with matching parameters and tie-break. Added 10 tests in `test/transactionsTool.test.ts` (descending order, `newestFirst` parity with `/income`, `limit 2`, same-date tie-break by id, distinct currencies, equal/distinct amounts). Runtime validation executed live (headless Chrome, license-activated device): three real same-date incomes created via `createServiceIncome`; `listServiceIncomes({ newestFirst: true })` (the exact call `/income` uses) returned `C(id 7, 1200€), B(id 6, 800€), A(id 5, 500€)`; `financial_transactions` with `limit:2` returned exactly `C(id 7, 1200€), B(id 6, 800€)` — an exact match. The real OpenAI provider conversation was not exercised in this validation to avoid unauthorized API spend; the fix was verified at the shared data-selection layer both consumers depend on, which is where the defect lived. Technical validation: full suite (106 files / 1493 tests), `npm run build` and `npm run lint` green, `git diff --check` clean.
- PB-IS-015.6 Insight Dashboard Runtime Integration implemented by replacing the Dashboard's disconnected data source with the same certified engines used by the financial conversation, and by fixing a confirmed React lifecycle defect that caused the literal infinite loading. Data-source fix: `insightDashboardUseCase.ts` replaces the previous legacy pipeline (`insightExecutionService` + `insightReadModels` + `FinancialSnapshotRepository.getLatestBySnapshotKey`, which depended on a sealed `PersistedFinancialSnapshot` that normal app usage never seals) with direct reads through `incomeService.listServiceIncomes`, `expenseService.listExpenses`, `earningPeriodService.getActiveEarningPeriod` and `settingsService.getSettings`, running `createFinancialInsightEngine()` and `createFinancialPlanningEngine()` (the same factories used by `aiConversationService.ts`) and producing a validated `InsightDashboardSnapshot`/`InsightDashboardViewModel` (`insightDashboardContracts.ts`, `insightDashboardMapper.ts`, `insightDashboardValidator.ts`). Exact root cause of the infinite loading (confirmed live in a headless-Chrome runtime session with instrumented logs, not by hypothesis): in `useInsightDashboard.ts`, the controller was created with `useMemo` outside the `useEffect`, so it survived the `mount -> cleanup -> mount` cycle that React `StrictMode` (enabled in `src/main.tsx`) runs in development; the phantom mount's `dispose()` permanently set `disposed=true` on that same instance while `state` stayed frozen at `loading`; the real remount then re-subscribed to that already-disposed controller, whose `load()` short-circuited on `state.status === 'loading'` (and any `emit` would have been dropped by `disposed` regardless). Fix: `useInsightDashboard.ts` now creates the controller inside the `useEffect` (a fresh instance per mount/cleanup cycle, tracked via `useRef` for `reload()`), so a phantom mount's disposal can never affect the real one. `insightDashboardController.ts` keeps the explicit `idle | loading | success | empty | partial | error` state machine with request-sequence guarding and a 10s local timeout. The Dashboard has no dependency on OpenAI or the conversational provider (verified by code inspection, a static test, and runtime observation — no OpenAI call occurred during validation). Runtime validation executed live against a real license-activated device (headless Chrome): (1) `loading` no longer persists indefinitely; (2) with no financial data the Dashboard shows the `empty` state with message and "Reintentar" button; (3) with real data inserted through the certified services (`createServiceIncome`, `createExpense`) the Dashboard reached `success`, showing 2 real insights ("Gasto por encima del ingreso", "Estado financiero general") and a Financial Action Plan with 4 recommended actions consistent with the real net balance (-EUR 250); (4) incomplete financial data (missing `eurValue`) is fail-closed rejected into an explicit `error` state instead of infinite loading; no console errors/warnings in any scenario. Technical validation: full suite (105 files / 1482 tests), `npm run build` and `npm run lint` green, `git diff --check` clean.
