- PB-IS-015.5-R2 Financial Transactions Ordering and Selection Consistency Repair implemented after empirically confirming (real Dexie, not hypothesis) that `/income` and `financial_transactions` diverged on same-date ties. Root cause: `/income` orders exclusively through `incomeService.listServiceIncomes({ newestFirst: true })` → `db.services.orderBy('date').reverse()`, whose reverse IndexedDB cursor resolves equal-date ties in descending primary-key (id) order; `financial_transactions` instead fetched ascending (`newestFirst: false`) and re-sorted with its own stable `Array.prototype.sort` comparator (`sortTransactions`), which preserves ascending order on ties — the exact opposite of `/income` whenever two or more incomes share a date (common, since `date` has day-level granularity only). Reproduced with three same-date incomes (A, B, C, created in that order): `/income` shows `C, B, A`; the tool previously returned `A, B, C`. Fix in `transactionsTool.ts`: (1) the income/expense fetch now derives `newestFirst` from the requested sort direction instead of a hardcoded `false`, aligning the base query with the same certified call `/income`/`/expenses` use; (2) `sortTransactions` gained a `recordId` tie-break (the record's real numeric id) applied with the same direction factor as the primary field, reproducing Dexie's actual reverse/forward cursor tie-break semantics instead of relying on `Array.sort` stability as an implicit (and wrong) tie-break. No second ordering engine or duplicated "latest incomes" definition was introduced; the tool still sources exclusively from `incomeService`/`expenseService`, now with matching parameters and tie-break. Added 10 tests in `test/transactionsTool.test.ts` (descending order, `newestFirst` parity with `/income`, `limit 2`, same-date tie-break by id, distinct currencies, equal/distinct amounts).
